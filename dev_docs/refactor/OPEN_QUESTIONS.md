## OQ-B7-01：截图/录屏中的彩色 emoji（当前决策已确认）

- **现象**：参考 Windows Terminal 会通过系统 emoji 字体显示彩色图形；当前截图栅格器使用 `fontdue` 灰度轮廓接口，不能绘制 COLR、CBDT 或 SVG 彩色字形。将这类字体当普通轮廓字体选择时，部分字形可能成为空白或缺字框。
- **上下文**：用户已确认 B7.3 纳入 Arabic/Indic 塑形和双向排布，并暂时使用单色 emoji。颜色 emoji 解码会影响截图与视频共同使用的字形栅格路径，超出单个 grapheme 修复。
- **候选方案**：
  1. 继续使用完整 grapheme 覆盖且能提供单色轮廓的字体；本轮默认采用此方案。
  2. 增加支持彩色字体表的栅格后端，或把彩色结果灰度化后输出；需要单独评估依赖和视频颜色契约。
  3. 没有单色字形时显示项目当前的确定性缺字回退。
- **后续影响**：方案 2 会影响 B7 PNG 与视频共用栅格配置。除非用户明确要求，本轮不扩大到彩色字形后端。
- **已确认决定**：当前按单色字形实现（用户于 2026-09-28 确认）。Windows 的 Segoe UI Emoji 可经 fontdue 轮廓栅格化为单色图形；其他平台按可用系统字体回退。
- **后续影响**：完整彩色支持仍需改造 PNG 与视频共用路径，但目前不属于未决行为。
- **状态**：本轮关闭；只有未来明确要求全彩 emoji 时再立项。

## OQ-B7-02：没有字体完整覆盖的 grapheme（高影响，B7.3 暂停点）

- **现象**：emoji ZWJ 或少见组合可能没有任何单一字体覆盖所有可见码点。逐字符换字体会在一个 grapheme 内混合字形基线和字重。
- **上下文**：B7.3 已按用户决定优先保留 grapheme 和终端样式语义。候选字体顺序固定；同一 grapheme 优先使用完整覆盖的同一字体。
- **问题**：当没有任何单一字体完整覆盖一个 grapheme 时，应该怎样绘制？该决定控制 cluster 拆分、fallback shaping 与跨字体定位，影响 B7 后续渲染验收。
- **候选方案**：
  1. 选可见码点覆盖最多的首个候选字体，缺失码点使用该字体的缺字形；目前实现的默认方案，可保持 grapheme 不拆分、位置确定。
  2. 允许同一 grapheme 分别从多字体补字；覆盖更全，但需确定分段塑形、基线和字重对齐规则。
  3. 丢弃整个 grapheme，保持布局最简单，但会丢失用户文本。
- **当前默认实现**：方案 1。`font_index_for_grapheme` 优先完整覆盖，缺少完整覆盖时按可见码点覆盖数选择候选字体；候选顺序固定。
- **后续影响**：方案 2 会扩展 fallback shaping 架构，牵涉 B7.3 与之后的渲染回归。本项视为高影响，B7.3 实现和当前自动测试通过后暂停该子阶段，先执行独立的 B8 主任务；用户答复后回到 B7.3 并继续 B7.4–B7.6。
- **状态**：待用户复核。当前实测系统字体完整覆盖 Arabic、Indic 与所选 ZWJ emoji 用例，所以本次自动测试没有命中该缺字回退分支。

## OQ-B9-01：Terminal 窗口失焦时文本输入的逻辑焦点与最终光标

- **现象**：系统 FocusLost 路径只清理 hover/按下状态，没有调用 `TextInputService::blur`；输入框仍可保持逻辑焦点。主循环因 `InputService::is_focused()` 将 IME policy 设为 Free，但 `route_render` 仍可能把活动输入框坐标交给 presenter。
- **上下文**：窗口失焦时保留文本输入焦点可在恢复窗口后继续输入；同时继续移动 terminal 光标可能影响系统 IME 的候选窗锚点。presenter 每帧只在输出末尾执行一次 `MoveTo`，没有向 IME 提供独立候选窗定位接口。
- **候选方案**：
  1. 失焦时 blur 文本框；恢复后用户重新聚焦。行为明显但会发出 Blur 事件并改变键盘路由。
  2. 保留逻辑焦点和文本，只在终端窗口失焦时令 `final_cursor=None`；这是当前默认候选，能保留编辑状态并阻止后台帧更新输入锚点。
  3. 保留逻辑焦点，并继续输出最终光标，依赖系统/终端管理失焦 IME。
- **当前默认**：用户已授权未决行为按默认推进；B9.3 采用方案 2：失焦时隐藏 `final_cursor`，不改输入缓冲与 Blur 回调。自动测试通过，白天仍可复核。
- **后续影响**：只阻塞 B9.3 失焦策略定稿；B9.2 静态/动效输出对照和 B9.1 自动坐标追踪可继续。
- **状态**：已按授权默认实施，待复核；不阻塞独立主任务。

回答：采用默认选项（方案2）即可。

## OQ-B10-01：Lua 宿主扩展的统一参数与复合返回协议（高影响，B10.2 暂停点）

- **现象**：实际注册的宿主扩展混用位置参数、数组表、命名参数表、直接标量、多字段结果表和异步 `HandleEvent`；例如 `encoding.base64_encode(bytes)` 是位置参数，`color.rgb{r,g,b}` 与 `draw.text{...}` 是命名表，`file.read{...}` 立即返回 nil（终态含 Session request id），而 B6 的 `image.load{...}` 会立即返回同一 request id。
- **上下文**：B10 目标要求统一扩展 API 的命名、参数和返回文档。Lua 5.4 标准函数/生命周期不在迁移范围；用户已明确项目内容不需要旧兼容，因此不保留旧 API 名称 alias。B2 的 string/math/utf8 项目式参数与结果表已单独确认，应继续按已确认契约处理。
- **候选方案**：
  1. 所有宿主扩展函数都接收一个命名参数表；一个简单结果直接返回标量，多个相关结果返回具名结果表；异步调用立即给 request id，终态事件回传同 id。调用名用清晰 `snake_case`，不保留旧 alias。（推荐，易统一静态检查与 IDE 提示。）
  2. 单一必需值函数保留直接参数；存在多个/可选字段时使用命名表；复合结果与异步关联同方案 1。改动小，但调用风格会保留两类。
  3. 保留各函数现状，仅修代码/文档不一致；对功能行为最保守，但不满足全局统一目标。
- **当前默认建议**：方案 1，同时保留已由用户特别确认的 B2 string/math/utf8 项目协议和 B6 image 契约；不把 Lua 原生函数纳入扩展包装。需要接收 nil 的扩展还依赖 OQ-B10-02 的显式 null 表示方案。将其余形状变更集中在一次升级中并给每个改动补完整调用样例/测试。
- **后续影响**：会改变大量现有包脚本的调用表达式、IDE 补全、文档和测试；本项目目前没有正式发布版且不需要兼容，但错误的整体形状仍会造成大量返工。先完成 API/事件盘点和文档漂移校正，暂停批量 API 签名迁移；按用户指示继续独立的异步生产事件与文档审计。
- **状态**：已确认方案 1。用户确认采用默认选项；B10.2 宿主扩展统一为一个命名参数表、简单结果返回标量、复合结果返回具名表、异步立即返回 request id 且终态回传相同 id。B2 string/math/utf8 与 B6 image 保留单独确认的契约；不保留旧 API alias。当前按组迁移。

回答：采用默认选项（方案1）即可。

## OQ-B10-04：loader 模块的多返回值与统一扩展返回契约

- **现象**：`loader.require/dofile` 将模块自身返回的任意 Lua 多返回值原样交给调用者；`loader.loadfile` 返回可执行函数。B10-01 已确认宿主扩展使用一个命名参数表、复合结果使用具名结果表，但 loader 的多返回值可能是 Lua 模块执行语义的一部分，而不是 loader 自身的复合查询结果。
- **上下文**：B10.2 正在迁移 loader 的参数形状。`loader.require("mod")` 会改成 `loader.require{path="mod"}`；返回值若改为 `{values=..., n=...}`，则所有加载器调用点和模块间约定都要改变，也可能损害模块组合方式。项目当前没有正式发布版，但模块业务语义仍需明确。
- **候选方案**：
  1. 只把 loader 路径参数改为 `{path=...}`，保留模块原始多返回值；把它记录为 loader 的专门透传契约。（推荐，保留模块可组合性。）
  2. 将 `require/dofile` 的结果统一包装为 `{values=..., n=...}`，并同步迁移脚本调用方；`loadfile` 仍返回函数。
- **当前建议**：方案 1。loader 的职责是执行/编译脚本，调用者消费的是模块自行定义的 Lua 返回值；这与宿主 API 自己组装的复合查询结果不同。
- **后续影响**：仅阻塞 B10.2 loader 结果形状及其文档/fixture，不阻塞 game/event/debug 的命名参数迁移。
- **状态**：已确认方案 1。用户明确选择保留模块原始多返回值；loader 参数按 `{path=...}` 统一，结果透传作为专门契约，并在文档与测试中说明。

## OQ-B10-02：Lua nil、JSON null 与统一命名参数（高影响，B10.4 序列化契约暂停点）

- **现象**：`serialization/value.rs` 将 Lua `nil` 编码为 JSON `null`，并把 JSON `null` 解码为 Lua `nil`。顶层可往返；但 Lua 表不能保存 nil 字段，因此嵌套 JSON 对象的 null 字段会消失，数组中的 null 会成为空位，再编码可能报稀疏数组错误或改变数据。
- **上下文**：B10.4 要明确 nil、空容器、数值边界和错误行为；B10.2 默认候选又要求所有宿主扩展采用单一命名参数表。Lua 无法把 `nil` 存入 `{ value = nil }`，所以统一表调用需要给 null 输入一个可表示的值。这个问题只影响序列化/API 协议，不阻塞其他文档和 fixture 盘点。
- **候选方案**：
  1. 增加只读 `serialization.NULL` 哨兵。JSON `null` 解码为哨兵，编码时哨兵输出 JSON `null`；顶层直接传 Lua `nil` 仍可编码 `null`。这样可保留嵌套对象字段和数组位置，并能放入命名参数表。（推荐。）
  2. 保持当前 nil 映射并明确文档告知嵌套 null 不可往返；不增加 API，但可能造成用户数据静默丢失。
  3. 命名参数统一规则对 null-capable 的函数保留直接单参数形式；不能用一个命名表表达该值，会留下协议例外。
- **当前默认**：未定项按用户授权默认推进，建议方案 1；它是一个明确、可序列化的 Lua 值，且能同时解决数组/对象 null 与命名表参数问题。实现前先完成当前独立文档与 fixture 盘点。
- **后续影响**：决定 JSON/YAML/TOML/CSV 中 null/空值语义以及 B10.2 序列化扩展的参数迁移形状。为避免在批量迁移中误定此语义，暂停 B10.4 序列化 null 行为定稿；先完成不依赖它的 B10.5 现有示例与测试锚点盘点。
- **状态**：已确认方案 1。用户确认 `serialization.NULL` 方案：JSON null 解码为只读哨兵，哨兵编码为 JSON null；顶层直接 Lua nil 仍编码为 null。哨兵保留嵌套对象字段与数组位置。跨格式范围按 OQ-B10-03 处理。

回答：采用默认选项（方案1）即可。
## OQ-B10-03：`serialization.NULL` 在非 JSON 格式中的语义

- **现象**：`serialization.NULL` 已确认用于保留 JSON null；通用 Lua↔JSON 转换也被 YAML、TOML、INI、XML 复用。YAML 能表示 null，TOML 没有 null，CSV/INI 的空字段或空值也无法区分 null 与空字符串；XML 当前没有定义 null 标记。
- **上下文**：若所有格式都把哨兵转为 JSON null 再交给格式编码器，会导致 TOML 编码失败、CSV/INI 可能静默变成空字符串，或 XML 输出出现未定义语义。B10.2 的 serialization 参数迁移依赖这一边界。
- **问题**：`serialization.NULL` 与各文本格式如何交互？
- **当前默认建议**：JSON 保持已确认的 null 往返；YAML 保留原生 null；CSV、INI、TOML、XML 的编码遇到哨兵时报带方法名的明确错误，不将 null 静默降为字符串/空值。解码端只有格式本身明确提供 null 时才返回哨兵；CSV/INI 空字段继续解为字符串。这样不会丢失类型信息。
- **后续影响**：影响 serialization API 参数迁移和格式边界文档；在回答前暂停 serialization 子组，不阻塞 encoding 与其他独立纯值 API。
- **状态**：已确认。用户明确选择 JSON/YAML 保留 null；CSV、INI、TOML、XML 编码遇到 `serialization.NULL` 时明确报错；格式本身不提供 null 的解码结果继续保持原有值类型。serialization 组按此契约实现。
